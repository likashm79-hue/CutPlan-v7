## Browser UI and naming check

The application source was loaded into headless Chromium with its local JavaScript modules inlined. This was necessary because the sandbox browser blocked navigation to the local HTTP server and `file://` URLs. The actual UI DOM and application event handlers were exercised:

- 35-piece mixed layout rendered 3 SVG board drawings, with 3 board names generated from `Bedroom wardrobe panel`.
- Individual board rename to `Bedroom side panel A` survived a prefix change and an identical optimization rerun; the content-derived internal board ID was unchanged.
- No browser page errors were reported.
- The browser context had an opaque origin, so `localStorage` was unavailable there. Persistence across a true page reload on a normal localhost origin is implemented in the app but was not directly verified in this sandbox.

## Worker check

A Chromium Blob Worker ran the production `nesting-worker.js` message handler with `nesting-engine.js` inlined in place of its relative `importScripts` dependency. The worker emitted progress updates and returned a validated result for 70 pieces. This verifies the worker message protocol and async engine execution. The regular same-origin `new Worker('./nesting-worker.js')` URL could not be exercised through a served page in this environment because browser navigation to localhost was blocked. The application fallback path was exercised successfully.

## PDF verification

PDFs were generated by Chromium's actual print renderer using the application's print stylesheet, then opened and inspected with PyMuPDF. They were not inferred from the presence of a print button.

**Mixed 35-piece case:**

- Exactly 3 pages.
- Each page measured approximately 595 × 842 pt (A4 portrait).
- Each page contained its corresponding custom board heading and part references/dimensions.
- All three rendered page images were visually inspected. Boards are centred, monochrome and portrait; part and board boundaries are solid; no edge-banding graphics or dashed overlays appear; no board title or part text is clipped.

**Small-part schedule stress case:**

- 70 pieces on one board, including 18 × 30 mm, 20 × 50 mm and 25 × 70 mm parts plus deliberately long part references.
- The first print check exposed schedule clipping. The print flex layout was corrected so the SVG board uses a fixed print height and cannot stretch the schedule out of the page.
- The regenerated PDF is exactly 1 A4 portrait page. Text extraction confirmed all four schedule rows including all references, dimensions and quantities; the rendered page was visually inspected and all markers correspond to schedule entries.

The in-memory Chromium harness used a main-thread fallback for the 35-piece application test because the local relative worker URL was blocked; the separate Blob Worker check above verified the worker protocol.

- The Full screen button was exercised with native Fullscreen API support in Chromium (enter and `document.exitFullscreen()`), and the CSS fallback was forced and tested separately (enter/exit both restored the expected state).

- The optimizer tests assert `offcutCount === sum(sheet.free.length)` and `reusableOffcutCount + unusableOffcutCount === offcutCount`. A board render displayed amber W01/W02 boxes and the schedule count matched the SVG overlay count exactly.
- Quick / Standard / Deep candidate targets are 12 / 64 / 192 (with up to four additional N−1 board-reduction probes on multi-board plans). The controlled v0.6.2 → v0.6.4 comparisons retained the same board count on all eight datasets at both Standard and Deep. Deep improved reusable offcut area by 156,613 mm² and reduced small scrap rectangles from 20 to 9 on the mixed-39 dataset. Details and the full per-dataset output are in `BENCHMARK-REPORT.md`.

Offcut highlighting is intentionally preview-only; the A4 print/PDF drawing remains the existing monochrome workshop drawing.
